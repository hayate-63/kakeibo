A. §0 家計簿コードとの差分確認（index-v5.1.html / GAS_v3.0.2 と照合済み）
================================================================
1. Logs の列（LOG_HEADERS）: 設計メモと一致
   id, amount, date, memo, category, useDate, payDate, payYM,
   useYM, bigCat, usageCat, budgetCat, absAmount, ruleId, isLegacy
2. evaluateEntry（引落日）: 設計メモどおり。ただし次の2点がメモに
   書かれていなかったので、家計簿に合わせて GAS を直した。
   - 休日 = 土日 ＋ loadAll が返す holidays（Googleカレンダーの
     日本の祝日。前年1月〜翌年12月）。計算式の祝日は、holidays
     が空のときだけ使う補助にした
   - adjust: 空欄のとき、カード・固定引落は "next"、それ以外は
     "none"（normalizeCategoryAdjust）。"none" なら補正しない。
     "prev" なら前の営業日へ、それ以外は後ろの営業日へ（最大15日）
3. DATA_REV: 設計メモどおり。POST は {pin, baseRev, logs}
   （action 無し）でよい。payload.logs が1件以上あるときだけ
   Logs シートを上書きし、送っていない dictionary／categories／
   budget／config／budgetMonthly のシートには触らない。
   ロックは waitLock(30秒) で、取れなければ busy。
   → 家計簿へ書き込む経路は、このコードの前提と合っている。
4. Config のキー: actualBalance / dodai_start_ym /
   dodai_start_balance / dodai_base / dodai_target。差分なし。
   ただしログ算出残高（calculateDodaiMetrics の logBalance）で、
   設計メモに無い2点を家計簿に合わせた:
   - dodai_start_ym が無いときの既定は "2026-10"
   - 「今月まで」の明細だけを数える（来月以降の分は入れない）
5. 予算（getEffectiveBudget）: BudgetMonthly の対象月の列は ym。
   bonusMonths は "," 区切りの月の数字だけ。家計簿と同じ読み方に
   直した。固定費の区分にはルール連動の特別な計算があるが、
   基準A／C は変動費だけを見るので影響しない。

B. §6 recalculateAllLogs の発動条件 ―― 【戻る（確認済み）】
================================================================
v5.1 では次のタイミングで recalculateAllLogs() が全明細に走る:
起動時、クラウド同期の後（syncFromCloud で毎回）、明細の追加・
削除・編集、マスタの変更、CSV 取込、給油明細の作成・削除 など。
中では evaluateEntry の結果 { category, useDate, payDate,
payYM, useYM, bigCat, usageCat, budgetCat, absAmount } で
各明細を上書きする。usageCat／budgetCat は「貯蓄移動などの
大分類 → treat（ローン・燃料）→ 辞書（メモの中の語）→
その他（要確認）／変動費（その他）」の順で決まる。
→ 本連携で直接入れた budgetCat（例「変動費（ガジェット）」）は、
  家計簿アプリで次に同期した時点で辞書判定に戻る。その次に
  家計簿アプリが保存すると、シートの値も書き換わる。
  商品名が辞書に無ければ「その他（要確認）／変動費（その他）」。
  その結果、ほしいもの帳の基準A（変動費の合計）は変わらないが、
  基準C（カテゴリー別）と家計簿の区分別の集計はずれる。
→ 直すには家計簿側の変更が必要（v5.2 案）。例:
  ・本連携の明細に印を付け、recalculateAllLogs ではその明細の
    usageCat／budgetCat を上書きしない。ただし LOG_HEADERS に
    印を入れる列が無いので、列を追加するか、ruleId に
    "wishlist" などを入れる（ruleId は定期ルールの照合
    relinkRecurringLogIds でも使われるので、影響を要確認）
  ・または、買った時に商品名を辞書に登録する
  v1.0 は設計どおり直接セットのまま。

  関連する注意: メモ（＝商品名）が「3/4 …」のように「月/日」で
  始まると、parseMemoLeadingDate が利用日をメモの日付に置き換え、
  メモからその部分を取り除く。商品名がそういう形のときは、
  再計算で利用月が変わることがある。

C. 家計簿と一致させられなかったもの
================================================================
- 「今日の1日予算」: 家計簿の renderDailyBudgetBanner は
  （変動費予算 − 使った額 − 予定からの予想 buildMonthlyForecast）
  ÷「出費予定のない残り日数」で、月末着地予想と同じ予定の見込みに
  頼っている（§4 で再現しないと決めた部分）。そのため v1.0 は
  「今日の1日予算（簡易）＝ 変動費残金 ÷ 今日を含む残り日数
  （マイナスは ¥0）」と画面に明記して出している。家計簿の数字とは
  一致しない。消す／v1.1 で予想を再現する、のどちらにするかは
  本人が判断。
- 防衛資金の到達遅延の土台ペース: 家計簿の計算では dodai_base が
  空なら 0 だが、本アプリは設計メモどおり 60,000 を既定にしている。

D. デプロイ手順（本人がやること）
================================================================
1. Google ドライブで新規スプレッドシートを作成（名前は任意、
   例「ほしいもの帳DB」）。
   メニュー「拡張機能 → Apps Script」を開き、コード.gs の
   中身を全部消して gas-v1.0.txt を貼り付けて保存。
2. 「プロジェクトの設定（歯車）→ スクリプト プロパティ」に追加:
     SECRET_PIN    = ほしいもの帳のパスワード（英数字・記号4〜64文字）
     HOUSEHOLD_PIN = 家計簿の PIN
3. エディタ上部の関数で setup を選び「実行」（初回は権限の承認）。
   items / categories（13件＋対応表）/ tags / settings
   シートができ、DATA_REV=0 が入る。
   （任意）testSummaryDummy / testPayDate を実行すると
   ログに計算結果が出る（家計簿へは書き込まない）。
4. 「デプロイ → 新しいデプロイ → 種類: ウェブアプリ」
   実行ユーザー: 自分 ／ アクセスできるユーザー: 全員
   → 発行された …/exec の URL を控える。
   ※ 以降 GAS を直したら「デプロイを管理 → 編集 → 新バージョン」
     で URL を変えずに更新する。
5. index-v1.0.html の先頭近くの
     const GAS_URL = 'https://script.google.com/macros/s/XXXXXXXX/exec';
   を 4 の URL に差し替え、Netlify（家計簿とは別サイト）へ
   index.html としてデプロイ。
6. iPhone でサイトを開きパスワードでログイン → 設定タブ:
   家計簿連携に家計簿 GAS の URL を入れて「保存」、
   「連携する」を ON。計算タブで家計簿の値（変動費残金・
   防衛資金枠）が出ることを確認する。
   → 家計簿アプリの表示と数字が一致するか必ず見比べる（「今日の1日予算（簡易）」は
     家計簿とは別計算なので一致しなくてよい）。
7. Safari の共有 →「ホーム画面に追加」。

※ 家計簿への書き込み（買った！）は、最初は少額のテスト商品で
  1回試し、家計簿アプリ側で明細が出ること・他の明細が消えて
  いないこと・購入済から「家計簿の明細も消す」で消えることを
  確認してから本運用に入ること。

E. 実装の要点
================================================================
- 通信は全て POST（text/plain JSON）で { action, pin, ... }。
  PIN を URL に載せない。家計簿 PIN はクライアントに一切出ない。
- 自前DB: DATA_REV ＋ baseRev で競合検出、LockService で直列化
  （取れなければ busy）、書く直前に bk_<シート>_<日時> の
  隠しシートでバックアップし 10世代でローテーション。
- 空上書きガード: (1) クライアントはサーバーから読み込めるまで
  保存しない（前回キャッシュ表示中は保存不可）。(2) GAS は
  2件以上あるシートを0件にする保存を拒否。(3) 削除は1件ずつ
  しか減らせない。(4) 家計簿へ送る logs は「取得件数＋1」
  「取得件数−1」以外なら送らない。家計簿が0件で返ったら送らない。
- 買った！: GAS の purchase が「自DBの rev 確認 → 家計簿
  loadAll → 新規1件を足して POST（conflict は loadAll から
  1回だけやり直し）→ 成功時のみ items 保存（householdLogId
  付き）」を1回のロック内で行う。家計簿側が失敗したら items は
  書かず、クライアントはシートを開いたまま赤バナーを出す。
  （家計簿 OK・自DB保存だけ失敗という稀なケースは、バナーに
   作成済みの明細 id を出す）
- 削除: householdLogId があれば「家計簿の明細も消す／
  ほしいもの帳だけ消す／キャンセル」を出す。家計簿側に既に
  その id が無い時は自DBだけ消して、その旨トーストに出す。
- 家計簿サマリーの前回値は GAS（HH_LAST）と端末の両方に保持。
  計算タブは古い値でも「○月○日 ○時 時点の値を表示中」付きで
  表示。欲しい物カードの「¥→¥」と詳細の影響行、タグ帯は
  このセッションで取得に成功した時だけ出す（ラベルが無いため）。
- ?add=<URL>: 起動時に検出してすぐ replaceState で消し、
  ログイン・同期後に読み取り → 確認カードを開く。
- URL 読み取り: 短縮URLは 3xx を自前で辿る。JSON-LD（@graph
  内も探索）→ OGP/meta → title の順。文字コードは
  ヘッダー／meta から判定（楽天の EUC-JP 等）。Amazon は
  /dp/ASIN に正規化しタイトルの「Amazon.co.jp:」を除去。
  取れなくても失敗にせず、手入力の確認カードへ。
- タグ絞り込みは複数選択時 AND（全部のタグを持つ商品）。
- PIN 照合は10回失敗で10分ロック（CacheService）。

   - loadAll → logs 全件＋1件 → POST {pin, baseRev: rev, logs}
   - saved → 成功（logId と家計簿の新 rev を返す）
   - conflict → loadAll からやり直して新規分だけ足し直し、
     1回だけ再試行。2回目も conflict なら失敗
   - unauthorized → 「家計簿の PIN が違います（HOUSEHOLD_PIN）」
   - busy → 「家計簿で他の保存処理中です」＋再試行ボタン

     busy → 再試行 → 成功の流れを確認。失敗時はシートと入力が
     残ることも確認）

6. 照合後の追加テスト: adjust 空欄 → next（12/26(土) → 12/28）、
