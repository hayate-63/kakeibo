・実機の前に、Drive の resumable upload の振る舞いを真似た模擬サーバを相手に、ブラウザ（Chromium）で画面側の処理を
　一通り動かし、9項目すべて PASS（§3）。iOS Safari・実 Google での確認の代わりにはならない
・特に重要な「Origin を Google へ転送できるか」は、実機で次の3つの根拠を自動で記録する（§1-1）：
　(a) GAS の UrlFetchApp が組み立てた送信ヘッダに Origin が残っているか
　(b) Google がセッション発行の応答に Access-Control-Allow-Origin を返したか
　(c) 画面から直接 PUT した時に CORS が通ったか（通らなかった時は、Google 側に届いたかを GAS から確かめて切り分け）
・Origin が送れなかった場合に備え、代替方式「GAS 中継チャンク」も同じ画面で試せるようにした（§1-5）

1. 作ったもの
==================================================
【構成】
・GAS（Code.gs）：PIN（スクリプトプロパティ SECRET_PIN）で守る API。画面に Google のアクセストークンは渡さない。
　画面に渡すのは resumable upload の「セッション URI」だけ（そのファイル1本だけに書き込める URI）
・HTML（index.html）：1枚で2通りの置き方に対応
　- GAS から配信（google.script.run で呼ぶ。画面の Origin は *.googleusercontent.com）
　- Netlify 等に置く（fetch で GAS の /exec に PIN 付き POST。画面の Origin はそのサイト）
　→ 画面の Origin が違う2つの置き方で、項目1の結果が変わるかを比べられる
・デプロイは「実行ユーザー：自分／アクセス：全員」（別オリジンから呼ぶため）。全ての操作は PIN 必須
・保存先：Drive 直下の「旅帳PoC」フォルダ（setup で作成）

【1-1 項目1：セッション発行（GAS）と Origin の転送】
・GAS が Drive API v3 の resumable upload（POST /upload/drive/v3/files?uploadType=resumable）を自分の権限で発行し、
　応答の Location（セッション URI）を画面へ返す
・「Origin を送る」「送らない」の2通りでテスト用の4バイトのセッションを作り、それぞれに画面から直接 PUT して比べる
・記録する根拠：
　- UrlFetchApp.getRequest() で見た送信予定ヘッダ（Authorization は伏せ字）と、その中に Origin が残っているか
　- Google の応答ヘッダのうち access-control-* と、全ヘッダ名
　- 画面からの直接 PUT の HTTP 状態（CORS で弾かれると 0）
　- 弾かれた時に、GAS からセッションの状態を問い合わせて、Google 側に届いていたか（届いていれば「送れたが応答が読めない」＝CORS）
・テスト用ファイルは終わったらゴミ箱へ

【1-2 項目2：直接アップロード】
・XMLHttpRequest で PUT（送信の進捗が取れるため fetch ではなく XHR）。チャンクは 256KB／1MB／4MB／8MB（いずれも 256KB の倍数）
・308 応答の Range ヘッダで受信済み位置を進める。Range が画面から読めない場合（Google が Expose しない場合）は、
　GAS から「bytes */総サイズ」で受信済み位置を問い合わせて続ける（どちらで進めたかを回数で記録）
・中断（通信断・5xx・タイムアウト）は、受信済み位置を確認して、そこから自動で再開（最大8回、待ち時間を倍々に）
・画面が隠れて戻った時（スリープ・アプリ切替）に止まっていたら、受信済み位置を確認して再開
・ページの再読み込み・アプリの終了後は、「未完了のセッション」からファイルを選び直すと途中から再開
　（iOS ではファイル本体を保存しておけないため、同じファイル名・サイズで照合して選び直してもらう）
・記録：ファイル名・形式（file.type）・サイズ・方式・チャンク・所要時間・速度・チャンク回数・308 回数・
　Range の読めた回数／GAS で確認した回数・中断と再開の理由と位置
・写真アプリから選ぶと iOS が JPEG／H.264 に変換することがあるため、HEIC・HEVC のまま試す欄（「ファイル」アプリ経由）を別に設けた

【1-3 項目3：表示・再生】
・サムネイル：GAS が自分の権限で Drive のサムネイルを取り、base64 で画面へ（共有設定なしで見られる方式）。
　読み込めたかを自動で記録
・原本をそのまま表示（8MB まで）：HEIC を Safari がそのまま表示できるかを自動で記録（img の onload／onerror）
・動画：Drive のプレビュー（埋め込み）と「Drive で開く」。埋め込みの再生は画面から判定できないため、
　見えたかどうかを判定ボタン（成／否）で記録。その時の共有設定（非公開／リンクを知っている全員）も一緒に記録
・共有 ON/OFF の切替ボタン（リンク共有なしでもプレビューが動くかを比べるため）

【1-4 項目4：参考計測（GAS 経由）】
・写真を base64 で GAS に送り、DriveApp.createFile で保存。全体の所要時間・base64 化の時間・GAS 内の時間を記録
・同じファイルを直接 PUT でも送って所要時間を並べられる

【1-5 代替方式：GAS 中継チャンク】
・Origin が送れず直接 PUT が CORS で通らない場合でも、画面 → GAS（base64 のチャンク）→ セッション URI の順で送れる。
　同じチャンク・308・再開の仕組みで動く。GAS の1回の呼び出しに載る量と実行時間の制限があるため、大きい動画では遅い見込み
　（実機で時間を記録して比べる）

【1-6 結果のまとめ】
・画面の［結果をまとめる］で、本報告 §2 にそのまま貼れる文章（項目ごとの成／否と根拠、iOS バージョン、ホーム画面アプリかどうか、
　画面の配信元、ファイル形式とサイズ、直近のログ）を作る。［Drive に保存］で「旅帳PoC」フォルダに PoC結果_日時.txt として残る
・結果とログは端末に残るので、途中で再読み込みしても消えない

3. 実装側で確認したこと（模擬サーバ相手・Chromium）
==================================================
・Drive の resumable upload の振る舞い（308＋Range、bytes */総サイズ での状態確認、セッション作成時の Origin に対してだけ
　CORS ヘッダを返す）を真似た模擬サーバを作り、画面を別オリジン（別ポート）から開いて、ブラウザ自身に CORS を判定させた
・9項目すべて PASS（test/poc.e2e.js、実行結果は 検証ログ-PoC-v0.1.txt）
　1 接続：別オリジンの HTML → GAS へ PIN 付き POST
　2 項目1：Origin あり＝直接 PUT 成、なし＝ブラウザのプリフライトで止まり Google 側にも届かない、判定「送れた」
　3 項目2：チャンク（1MB）・308 で進捗・一時エラー（503）と通信断（オフライン 2秒）から自動再開。届いた中身の md5 が元と一致
　4 項目2：308 の Range ヘッダが画面から読めない時は GAS で受信位置を確認して完走（md5 一致）
　5 代替：Origin なしのセッション（直接 PUT 不可）でも GAS 中継チャンクで完走（md5 一致）
　6 項目2：一時停止 → ページ再読み込み → 同じファイルを選び直して途中（2MB）から再開して完走（md5 一致）
　7 項目3：サムネイル（GAS 経由）の表示と判定の記録
　8 項目4：GAS 経由の保存と所要時間の記録
　9 結果のまとめ（§2 に貼る形の文章が出る）
・途中で分かったこと：Chromium は「使い回した接続が切れた」時に PUT を自動で送り直すため、接続を切るだけでは中断が再現しなかった。
　実機でも、短い通信断はブラウザが黙って送り直し、中断として記録されないことがある（それ自体は問題ではない）
・GAS（Code.gs）と HTML の構文は node --check で確認。GAS は実行していない（実 Google の API に届かない環境のため）

4. 既に分かっていること（文献）と、実機で決まること
==================================================
・Google Cloud Storage の resumable upload では、ブラウザから送る場合「セッションを作る時の要求に Origin ヘッダを付ける」ことが
　公式に案内されており、作成時の Origin に合う時だけ Access-Control-Allow-Origin が返る。Drive API で同じ扱いかは文献で確認できず、
　また GAS の UrlFetchApp が Origin ヘッダをそのまま Google へ送るかも公式の記載を確認できなかった → 項目1の実機結果で決まる
・セッション URI は約1週間有効で、その間はそのファイル1本に書き込める（アクセストークンではないが、漏れれば上書きされうる）。
　画面に置くのはアップロード中の間だけにし、完了・破棄で端末から消している
・Wi-Fi／モバイル通信の判定は入れていない（引き継ぎメモどおり、範囲外）

5. 実機の結果で決まる次期モデルの方式（判断の目安）
==================================================
・項目1 で Origin が送れて直接 PUT が通る → 写真・動画とも「GAS がセッション発行、画面から直接 PUT」を本命に
・Origin が送れない／CORS が通らない → 小さい写真は GAS 経由（項目4 の時間を見て）、動画は GAS 中継チャンク（§1-5）で
　実用になる速さかを見て判断。だめなら別の受け口（Drive 以外の保存先 等）を検討
・項目2 の再開が実機で通らない → 動画は自動送信を既定にせず、保留（手動送信）の既定（代替仕様 C）を強める
・項目3 で HEIC の原本表示ができない → 表示は Drive のサムネイル（GAS 経由）に統一。動画のプレビューが共有なしで再生できない →
　「Drive で開く」を主、埋め込みは共有した時だけ
